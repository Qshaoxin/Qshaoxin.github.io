「遇动」是一个校园智慧体育服务小程序：场馆预约、运动搭子匹配、赛事报名、体测备考、器材共享、打卡积分，六个模块。它是中国国际大学生创新大赛（2026）的参赛项目——从产品设计、前后端开发到服务器部署运维，全部由我一个人完成。这篇文章记录它从一份 Word 计划书到真实上线跑通的全过程，以及踩过的每一个坑。

## 起点：一份计划书和两天时间

接手时只有一份填了一半的计划书模板：四大痛点（约球难、场地预约难、运动社群零散、体测备考），六大功能模块，还有一个域名和一台学生价云服务器。

距离校赛材料提交只剩两天，我做了个决定：**不赶材料，先把东西做出来**。一个能扫码跑起来的产品，比任何 PPT 都有说服力。

于是整个开发节奏变成了：第一天搭完工程骨架 + 设计系统 + 场馆预约闭环，第二天补齐搭子社交、赛事、体测、器材、积分全部模块，第三天部署后端上线。回头看，能在这个节奏下完成，前期两个技术决策功不可没。

## 选型：原生小程序 + 双通道数据层

前端选了**原生小程序**而不是 uni-app / Taro。理由很实际：零 npm 依赖、微信开发者工具打开即跑、构建链路上没有会挂掉的环节。对这种一个人扛全部的项目来说，「稳定能跑」比「技术先进」重要得多。

真正花心思的是数据层。一开始没有小程序 AppID，云开发联调不了——很多项目会卡在「先去注册、等审核」这一步。我做了个双通道设计：

```
services/（业务接口层）
   ├── useMock = true  → 本地演示数据库（storage 持久化，无需任何后端）
   └── useMock = false → wx.request → 自建后端 REST API
```

所有页面只认 `services` 暴露的接口，底下接的是本地 mock 还是真实服务器，一个开关切换。这个设计让「开发」和「上线」解耦了——没有 AppID 的第一天就能把全部功能做完，后端就绪后一行代码切过去。

后端最终选了自建而不是微信云开发：Node.js + Express，数据库用最朴素的 JSON 文件持久化（内存缓存 + 防抖落盘）。演示规模下这比引入 MongoDB 更稳，而且备份就是复制一个文件。API 设计成 `/api/:领域/:动作` 的路由风格，和云函数结构一一对应，迁移成本为零。

## 图标：从 emoji 到一套 SVG 图标库

中途给自己定了个硬要求：**界面图标全用 SVG，禁止 emoji**。这时项目里已经到处是 emoji 了（场馆、器材、商品、赛事数据里全是 `🏟️` `🏸`）。

没有引入图标字体库，而是手写了一套集中管理的 SVG 图标库：61 个 24×24 线性图标（运动项目、功能、导航）放在一个 `icons.js` 里，作为全局唯一图标源。小程序的 image 组件不能直接用 SVG 文件，就写了个 `qd-icon` 组件，运行时把 SVG 字符串转 base64 data-uri 渲染。

tabBar 是个例外——微信的 iconPath 只接受 PNG。于是用 Node 脚本 + resvg 从**同一份 SVG 源**转出 PNG，图标只设计一次，两处使用。改任何图标，跑一遍 `gen-icons.js` 全部同步。

## 部署：在一台共享服务器上「见缝插针」

服务器上已经有别的服务在跑（80 端口有别的站、3000 和 8081 有其他应用），不能动。最终的部署结构：

```
微信小程序 → https://campuslife.top/qd/* → nginx 443（Let's Encrypt 自动续期）
    → 127.0.0.1:8300 Express（pm2 守护）
    → JSON 持久化 data/db.json
```

几个细节：

- API 挂在独立路径 `/qd/` 下，反代到空闲的 8300 端口，和已有站点互不干扰
- 域名解析早已指向这台机器，用 certbot webroot 模式十分钟签好证书
- 部署脚本化：本地打包（排除 node_modules）→ sftp 上传 → 远程解压安装 → pm2 重启，一条命令完成重新部署
- 后端上线后写了一个 23 项断言的 API 闭环测试脚本（登录→预约→发动态→匹配→报名→租借→打卡→兑换），本地和公网各跑一遍，全绿才算部署成功

## 踩坑记录

这部分是这篇文章最想沉淀的内容，每一个都是真实花时间排查过的。

**1. WXML 不支持函数调用。** 多选标签的选中态写成 `{{list.indexOf(item) > -1 ? 'on' : ''}}`，点上去毫无反应、也不报错。原因是 WXML 数据绑定只支持简单表达式，`indexOf` 这种方法调用静默失败。解法：选中态在 JS 层维护（每个选项带 `on` 字段，`setData` 精确更新）。登录页的运动/时间多选、匹配页、场馆时段选择，三处统一改掉。

**2. 测试号不能上传体验版。** 这不是 bug，是平台规则——测试号只能本地调试。老老实实注册个人主体小程序（免费，5 分钟），换上正式 AppID。

**3. 合法域名配置了，真机还是被拦。** `request 合法域名`里明明保存了 `https://campuslife.top`，非调试模式下依然提示网络失败。排查路径：先确认服务器公网正常（API 测试全绿）→ 确认报错来自 `wx.request` 的 fail 回调 → 把错误提示改成带出 `errMsg` 原文，确认是 `url not in domain list`。结论：**微信域名白名单的生效有延迟**，从几分钟到几小时不等，期间开发调试靠「详情→不校验合法域名」（工具）和「开发调试」模式（真机）绕过。这题没有技术解，只有耐心。

**4. `wx.getUserProfile` 已经废了。** 想做「微信一键登录」，旧 API 返回的全是匿名信息（「微信用户」+ 灰头像）。2023 年后的正解是官方的头像昵称填写能力：`button open-type="chooseAvatar"` 取头像 + `input type="nickname"`（键盘上方会弹「使用微信昵称」快捷键）。头像文件以 base64 JSON 上传到服务器存盘，静态路由对外提供，跨设备可见。

**5. 一个微信号只有一个账号，靠的是 openid。** `wx.login` 拿临时 code，服务器用 AppID + Secret 调 `code2Session` 换 openid。同一个微信号在同一个小程序里的 openid 永远不变，登录逻辑写成「按 openid 找用户，有则更新、无则创建」，天然保证不重号，换设备登录也是同一账号。

**6. tar 会把 `C:` 当远程主机。** Windows 下给 GNU tar 传 `C:\path` 打包，报 `Cannot connect to C: resolve failed`——盘符冒号撞上了 tar 的 `host:path` 语法。解法是转成 `/c/path` 形式或加 `--force-local`。

**7. 外部推送没有免费午餐。** 「有人加入你的约运动时发微信通知」——微信订阅消息是「用户授权一次、才能发一条」，不存在长期推送。管道做了双层：站内通知（消息中心 + 首页铃铛红点 + 横幅）永远可用；外部服务通知在用户发布动态时弹一次订阅授权，按次数消耗。模板还要在 mp 后台申请、服务器 IP 要进白名单，一步都省不掉。

## 现状

- 19 个页面、6 大模块、8 个领域后端服务，全部上线在 `https://campuslife.top/qd`
- 体验版已可扫码使用，测试用户的真实数据开始进库（演示数据已清空）
- 比赛计划书里的名字叫「趣动青春」，小程序品牌改过两次名：趣动青春 → 小青松 → 遇动。「遇」是相遇，「动」是运动——遇见想一起运动的人，这大概就是这个产品最核心的一句话。

## 一点感受

这个项目最大的收获不是小程序本身，而是验证了一套打法：**先用最小闭环跑通端到端，再往两边长**。第一天结束时有完整的设计系统和一条能预约场馆的链路，后面每个模块都是在已验证的地基上砌墙；双通道数据层让「后端没就绪」从不阻塞前端；每次部署后跑一遍 23 项的 API 回归，改坏了立刻知道。

两天写完不神秘——是结构对了。
